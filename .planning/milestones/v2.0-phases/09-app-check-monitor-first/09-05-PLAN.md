Firebase Auth INDEPENDENTLY awaits an App Check token before sending signUp (AuthImpl._getAdditionalHeaders → _getAppCheckToken → app-check-internal getToken, building the X-Firebase-AppCheck header). With reCAPTCHA scripts network-blocked (ad-blocker visitors — the exact population runbook §8 measures), the Enterprise provider's script tag hangs forever (onload only, NO onerror — CDN-pinned 12.18.0 code you cannot patch), so the SDK-internal header await hangs until Auth's own NetworkTimeout (Delay 30s desktop / 60s mobile UA) rejects with an auth-family error → signUp never sent → addDoc never runs → generic error status, no Firestore doc, no event. Observed ~60s ≈ 10s race + 30/60s timeout.

Fix direction (from debug session .planning/debug/token-failure-auth-network-failed.md): probe reCAPTCHA reachability BEFORE App Check init; on probe failure skip init entirely — with no registered app-check service, the Auth SDK's optional header lookup returns undefined and short-circuits, so auth + addDoc proceed fast un-attested (~10s bound restored) and the appcheck status + consent-gated event fire per the established G-09-5B semantics.

**Design question resolved (planner decision, documents the debug session's open item):** D-06/D-07 need NO extension. The probe eliminates the scenario instead of remapping auth-family codes — probe failure surfaces as a synthetic appCheck/*-family code through the EXISTING single mapping point. The mapping spec (D-06/D-07) stays byte-identical.

Plan-around-not-through: the hang mechanism lives in gstatic CDN-pinned SDK code (12.18.0 exact pin) — the fix avoids the hang (never registers the app-check service when reCAPTCHA is unreachable) rather than attempting to patch or bound the SDK-internal await.

Purpose: the §8 ad-blocker metric must be able to SEE the population it targets — today a blocked-reCAPTCHA submit produces an auth-family error that is invisible to the appcheck status, the un-attested delivery, and the event.

Add a bounded reachability probe so App Check is never initialized while reCAPTCHA is unreachable — eliminating the SDK-internal header-await hang at its only entry point (the registered app-check service instance). Touch nothing else: honeypot swallow, validation, double-submit guard, lazy import, init order, dormant gate, raceToken, record-and-swallow catch, post-delivery re-throw, onSubmit mapping (D-06/D-07), and consent.js all stay as shipped by 09-04.

1. Add a `PROBE_TIMEOUT_MS = 3000` constant beside the other module constants. Rationale: the probe guards the only hang entry point (App Check registration), and an unbounded probe would reintroduce the same deadlock class it exists to remove. DevTools/ad-blocker blocks reject the probe fetch near-instantly, so the blocked scenario pays ~0ms; a healthy connection pays one no-cors fetch (~100-300ms) once per session.

2. Add a local helper (inside the IIFE, zero new globals) that resolves to a promise of the App Check instance or null, given the mods namespace, the default app, and the config:
   - If the cached `appCheckInstance` exists (a previous submit initialized it), resolve with it immediately — no probe, preserve the cache-once guard.
   - Otherwise probe reachability: fetch the exact script URL the SDK itself loads for the Enterprise provider — the production JS host plus the render=explicit query — in `mode: 'no-cors'` with `cache: 'no-store'`, raced against the probe timer. Exact-pinned 12.18.0 makes this URL stable; a deliberate future version bump must re-verify it (document in the inline comment).
   - On probe success (opaque response), run the existing init (cache-once assignment into `appCheckInstance`, ReCaptchaEnterpriseProvider with the config site key, isTokenAutoRefreshEnabled false) and resolve with the instance.
   - On probe failure (reject OR timer), record the synthetic failure code `appCheck/probe-failed` into the shared failure-code variable and resolve with null — init is NEVER called, so no app-check service is registered on the app.

3. Rewire the active-site-key branch of the App Check block so it chains: prepare (the helper above) → when non-null, the existing raceToken around the explicit getToken with its record-and-swallow catch → proceed. When null (probe failed), skip the explicit gate entirely — there is no instance to call it with — and let the chain proceed directly to auth + addDoc. The recorded probe code flows out through the EXISTING post-delivery synthetic re-throw, so the onSubmit catch remains the single mapping point (D-06/D-07 unchanged): appcheck status shows, persano:appcheck dispatches, consent.js routes it to the consent-gated event, form stays usable and unreset, no auto-retry. The dormant branch (empty site key) stays byte-identical: no probe, no init, no recorded failure.

4. Why this kills the hang (encode in comments, not in behavior): with no registered app-check service, the Auth SDK's optional app-check lookup for the X-Firebase-AppCheck header returns undefined and the optional-chain short-circuits — there is no token await left to hang, so the signUp fetch goes out immediately and addDoc follows. The same absence protects any Firestore attestation ride. The provider's script-tag hang (onload only, no onerror) lives in gstatic CDN-pinned code that cannot be patched — skipping registration is the only lever.

5. Document the accepted residual edge in the inline comment: a visitor who completes one attested submit (instance cached) and THEN enables a reCAPTCHA blocker mid-session re-enters the SDK-internal hang (12.18.0 offers no un-registration) — bounded only by the Auth NetworkTimeout as today. Fresh environments — the UAT test-7 scenario and the dominant ad-blocker case — are fully covered. Accepted, not engineered around.

6. Update the header comment (lines ~11-30) and the App Check block comment (~181-197): the pipeline is now probe-gated — reCAPTCHA unreachable (probe reject/timeout ~3s) → App Check skipped entirely, message delivered un-attested fast with the appcheck status + consent-gated event; reCAPTCHA reachable → unchanged bounded explicit-gate semantics; D-06/D-07 mapping and no-auto-retry unchanged. Keep the banner-independence statement true: no new module imports, no reads or writes of any banner storage key, the Analytics-module import stays absent from this file. Write comments without the call-paren form of the init function name (comment prose says "the App Check init call") so the call-site count gate stays meaningful.
